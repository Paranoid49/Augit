# Augit 实施路线图

本文记录 Augit 从空仓库到首个可发布版本的实施顺序、状态和完成条件。产品行为以[产品规格](product-spec.md)为准，技术方案以[架构说明](architecture.md)为准；本文不得新增产品能力。

本路线图是可复制到任意干净电脑的重建基线，不包含旧仓库路径、旧提交号、旧实现状态或旧电脑性能数据。复制文档后，除已经确认的产品与架构决定外，所有代码实现项都从未完成开始。

## 1. 状态说明

- `[x]`：已经确认或已经实现并通过当前阶段所需验证。
- `[ ]`：尚未实现或尚未在当前重建仓库中验证。
- 每个阶段必须形成可启动、可测试的版本，禁止长期保留只有后续阶段才能运行的半成品。
- 后一阶段可以做技术预研，但不得绕过前一阶段的完成条件宣布完成。
- 完成项必须在当前仓库附上可复现证据，不得沿用其他电脑或旧实现的结论。

当前里程碑：**原生 Win32 阶段一至阶段四已完成，阶段五实现、Windows 11 性能验收及管理员安装、升级覆盖和卸载验收已完成；仍等待 Windows 10 22H2 验收，不得提前宣布阶段五或首版完成**。

- [x] 支持多标签、行号、复制、当前文件查找和关闭标签。

### 3.6 当前验收证据与性能结论

- 2026-08-27 的当前实现通过 45 项自动化测试，其中核心 17 项、基础设施 19 项、界面 9 项；Release 零告警构建、格式检查和随包 ripgrep `15.2.0` 版本检查通过。
- 使用实际发布版完成阶段一界面烟雾检查：普通 UTF-8、带 BOM UTF-8、严格格式化 JSON、非法 JSON 行列提示、超过 10 MB 文本、PNG/JPEG/BMP、损坏 PNG、GIF、WebP、PDF 类二进制和非法 UTF-8 均显示正确，摘要场景均保留外部打开入口；多标签和只读文本界面同时得到验证。
- Markdown 实际预览验证覆盖标题、任务列表、表格、删除线、自动链接、原生 HTML 转义、工作区内链接和本地 PNG。检查中发现并修复首次内部导航被安全拦截而显示空白，以及切回原文未释放 WebView2 的问题；工作区内链接能够打开对应只读 Markdown 标签。
- Markdown 预览连续打开和关闭 10 次，每次真实内容在 `609–649 ms` 内出现，每次关闭后六个 WebView2 子进程在 `416–434 ms` 内全部退出。第一次关闭并空闲 10 秒后主进程 Working Set 为 `202.17 MiB`，第十次关闭并空闲 10 秒后为 `198.73 MiB`，没有持续增长。
- 已打开 Markdown 文件的外部修改在 `181 ms` 内反映到界面；快速打开和全仓搜索通过实际界面验证。临时创建的目录联接在文件树中为不可展开叶节点。
- 10 万文件诊断工作区由 100 个目录、每目录 1000 个文件组成；发布版首次诊断的窗口响应为 `1245 ms`，空闲 5 秒 Working Set 为 `180.60 MiB`，空闲两秒 CPU 时间增量为 `0 ms`，核心启动没有 WebView2 子进程。
- 修复未显示窗口退出时的非有限坐标序列化问题后，同目录第二实例在 `438 ms` 内以退出码 `0` 结束。
- 同机最小空白 .NET 10 WPF、Release、`win-x64`、非 self-contained 首次诊断的窗口响应为 `529 ms`，空闲 5 秒 Working Set 为 `115.17 MiB`，空闲两秒 CPU 时间增量为 `0 ms`。
- 第二次采用相同发布方式交替测量三轮。空白 WPF 的窗口响应为 `666/402/400 ms`，Working Set 为 `114.83/105.93/106.19 MiB`，Private Working Set 为 `46.83/43.36/43.61 MiB`；Augit 的窗口响应为 `513/516/517 ms`，Working Set 为 `155.68/157.95/158.21 MiB`，Private Working Set 为 `81.68/81.84/82.13 MiB`。两者均只有一个进程，空闲两秒 CPU 时间增量均为 `0 ms`。连续启动受文件缓存影响，不能替代正式冷启动验收。
- 诊断机为 Windows 11 25H2 `10.0.26200.9168`、16 个逻辑处理器、31.29 GiB 内存，实际使用 .NET Desktop Runtime `10.0.5`。进程模块复核发现 Nahimic 的 `AudioDevProps2.dll` 同时注入空白 WPF 和 Augit；该模块具有有效签名，注入服务处于运行状态。Augit 未额外加载 WebView2、Markdig 或 AvalonEdit，也未创建 WebView2 子进程。
- 上述带 `AudioDevProps2.dll` 的结果只保留为诊断历史，不用于正式判定。获得用户授权后，正式复测在测量窗口内停止 `NahimicSvc64`、`NahimicSvc32` 和 `nahimicNotifSys`，并逐个核验 Augit 与空白 WPF 的全部模块；目标进程均未加载 Nahimic、E-SafeNet 或任何应用目录、Windows、.NET Runtime 目录以外的模块。
- 正式首轮使用相同的 10 万文件 Git 仓库和 Release、`win-x64`、非 self-contained 发布版。Augit 从创建进程到窗口完成合成并响应窗口消息为 `911.77 ms`，空闲 5 秒后的单进程 Working Set 为 `155.09 MiB`，私有内存为 `96.89 MiB`，空闲两秒 CPU 时间增量为 `0 ms`；因此冷启动硬指标通过，核心 Working Set 硬指标未通过。
- 为排除内存瞬时波动，又完成两轮相同测量。Augit Working Set 为 `155.54/155.27 MiB`；同发布方式的最小空白 .NET 10 WPF 三轮 Working Set 为 `105.47/99.73/105.40 MiB`，平均 `103.53 MiB`。空白 WPF 基线已经跨过 `100 MB` 阈值，无法为实际应用留下稳定内存预算；Augit 三轮结果则稳定高于阈值约 `55 MiB`。
- 继续以无注入环境分解 Augit 自身成本：完全不打开工作区时 Working Set 已为 `135.71 MiB`，打开普通工作区后为 `144.75 MiB`。`GCConserveMemory`、关闭并发回收、关闭分层编译和关闭诊断端口的单项及组合测试结果均为 `144.16–144.77 MiB`，最多只节省约 `0.6 MiB`；关闭预编译映像反而使启动增至 `1376.48 ms`、Working Set 增至 `154.71 MiB`，因此这些配置均不构成有效优化。
- 对无工作区主窗口强制完整 GC 后采集托管堆，存活对象共 `27151` 个、仅 `1.83 MiB`，此时进程 Working Set 仍为 `137.76 MiB`。超出硬指标的主体不是 Augit 业务对象或可回收托管堆，而是 WPF、CLR、字体、渲染和本机模块的基础工作集；删除阶段一功能或增加启动 GC 都无法弥补约 `38 MiB` 的差额。
- 为区分 C#/.NET 与 WPF 的成本，又在同机测量 C#、.NET 10、Release、`win-x64`、非 self-contained 的原生 Win32 空窗口，窗口尺寸同为 `1180×760`。无注入首轮启动为 `142.13 ms`、空闲 5 秒 Working Set 为 `24.23 MiB`，后两轮为 `66.91/57.44 ms` 和 `24.08/24.07 MiB`；因此硬指标的主要障碍是 WPF 桌面栈，而不是 C#、.NET 10 或窗口尺寸。保留现有 Core 与 Infrastructure、仅将 WPF 应用外壳改为原生 Win32 具有足够性能余量，但这仍属于架构变更，未经用户明确确认不得实施。
- 2026-08-27 用户明确确认保留 C# 与 .NET 10、将 WPF 应用外壳迁移为原生 Win32，并继续保持 `1 秒` 与 `100 MB` 硬指标。WPF 性能结果自此只作为迁移原因和行为基线，不能代表新架构验收结论。

## 8. 跨阶段固定约束

- 普通查看器不提供编辑和保存；用户主动执行的 Git 操作可以由本机 Git 修改工作区；只有冲突最终结果区允许用户直接编辑并保存文本。

- 不支持 AI 集成、Git 子模块、GitHub/GitLab 平台接口、Force Push 和单窗口多仓库。
